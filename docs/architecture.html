PART B · ARCHITECTURE

תכנון המעבר ל-Microservices

חמישה שירותים עצמאיים — Customers, Requests, Documents, Notifications, Reporting — כל אחד עם בסיס הנתונים שלו, רצים על Azure, מדברים דרך Gateway אחד ו-Bus אחד.

כל שירות אחראי אך ורק על התחום שלו: הוא הבעלים היחיד של הנתונים שלו, ואף שירות אחר לא ניגש אליהם ישירות. קריאה שדורשת תשובה מיידית עוברת דרך ה-Gateway. עדכון ששירותים אחרים צריכים לדעת עליו לא נשלח אליהם ישירות — הוא מתפרסם כאירוע ב-RabbitMQ, וכל שירות שמעניין אותו האירוע מאזין לו בעצמו. שירות ה-Requests שכבר בנינו בחלק א׳ הוא נקודת ההתחלה.

01טופולוגיה

02מי אחראי על מה

  • Customersפרטי לקוח, איש קשר, סטטוס KYC.
  • Requestsמחזור החיים של הבקשה — סטטוס, סוג, שיוך. (חלק א׳)
  • Documentsמסמכים שמצורפים לבקשה או ללקוח, כולל קבצים בפועל.
  • Notificationsשליחת מיילים/התראות כשמשהו קורה במערכת.
  • Reportingדוחות וניתוחים על פני כל השירותים.

03איך הם מדברים

סינכרוני, דרך ה-Gateway: רק כשחייבים תשובה באותו רגע — כמו כשה-Angular מבקש רשימת בקשות. ה-Gateway גם מאמת את המשתמש (JWT), כך שכל שירות שמאחוריו כבר סומך על הזהות שהגיעה אליו.

אסינכרוני, דרך ה-Bus: זה המקרה הנפוץ בין שירותים. לדוגמה: כש-Requests יוצר בקשה חדשה, הוא מפרסם אירוע RequestCreated. הוא לא קורא ל-Notifications או ל-Reporting בעצמו ולא מחכה לתשובה מהם — הם מאזינים לאירוע ומגיבים בזמן שלהם. אם Notifications נופל לרגע, Requests ממשיך לעבוד כרגיל.

04טכנולוגיות

GatewayAzure API Management — נקודת כניסה יחידה, מנתב וגם מאמת JWT.
תור הודעותRabbitMQ — רץ כ-container בתוך Azure Container Apps; exchange לכל domain.
AuthMicrosoft Entra ID — מנפיק את ה-JWT; מחליף את ה-headers מחלק א׳.
בסיס נתוניםAzure SQL Database — מופע נפרד לכל שירות.
קבציםAzure Blob Storage — לקבצים בפועל של שירות Documents.
הרצהAzure Container Apps — container ו-deploy נפרדים לכל שירות.
CI/CDAzure DevOps — pipelines נפרד לכל שירות, אותו repo-per-service.

05מסלול המעבר

לא במכה אחת. חותכים חתיכה אחת מהמונוליט בכל פעם.

06תרחיש: התראה אמינה כש-Status משתנה

אם Requests היה קורא ל-Notifications ישירות וממתין לתשובה, נפילה זמנית של Notifications הייתה גוררת אחת משתי בעיות: או שיצירת הבקשה נחסמת (למרות שאין לזה שום קשר להתראה), או שההתראה פשוט אובדת בשקט. שתי האפשרויות רעות. הפתרון: Requests לא קורא ל-Notifications בכלל — הוא רק מפרסם אירוע לתור, וארבעה מנגנונים דואגים שההודעה תגיע גם אם Notifications למטה.

PART C · CLOUD DEPLOYMENT

איך זה יושב בפועל על Azure

חלק ב׳ הראה את הארכיטקטורה הלוגית — מי מדבר עם מי. זה הפריסה הפיזית — איפה כל דבר רץ, איך הוא גדל, ואיך יודעים שהוא בריא. הכול בסביבת Azure אחת, כל ההחלטות מ-חלק ב׳ (Gateway, RabbitMQ, Entra ID) נשארות כמו שהן.

ComputeAzure Container Apps — כל שירות ב-container נפרד, deploy ו-scale עצמאיים.
DBAzure SQL Database — מופע נפרד לכל שירות; ל-Requests (מיליוני רשומות, חלק א׳) נוסף read replica לשאילתות חיפוש.
MessagingRabbitMQ — cluster של 3 nodes עם disk מתמיד, לזמינות גבוהה ולתורים durable.
MonitoringAzure Monitor — Application Insights לכל שירות (traces לפי correlation-id), Log Analytics מרוכז, alerts על error rate ואורך תור.
ScalingContainer Apps autoscale (KEDA) — לפי concurrent HTTP requests בשירותי ה-API, ולפי אורך תור RabbitMQ ב-Notifications.
